# 方案一：按需链路日志采集与存储改造（消息链路查询 SVIP 对外服务）

| 项目 | 内容 |
|---|---|
| 发起部门 | 技术支持部门 |
| 评估/配合部门 | **研发部门**（采集改造、存储改造、查询接口）、**运维部门**（Redis/冷存储容量、监控） |
| 文档状态 | 待评估（V1.0，2026-10-27） |
| 关联文档 | 《方案二-异步队列限流查询》（轻量替代路线，见文末对比） |

---

## 1. 背景与现状

### 1.1 现有能力

- 开发者平台「故障排查 → 消息链路查询」已规划为 **SVIP 功能**，页面已有展示位：输入 `taskid + cid`，返回该条消息的下发链路时间线（受理 → 个推下发 → 厂商通道 → 到达/失败）。
- 链路数据目前由下发链路各模块产生，**存储在 Redis**，默认保留 **7 天**（可调整为 30 天）。
- 该能力当前定位为**全量记录**：所有设备的消息链路都会写入，存储成本随消息总量线性增长，是存储压力的主要来源。

### 1.2 需求

- 客户（开发者）在 SVIP 入口**批量上传 10~20 个设备 cid**，系统只对这些设备**按需开启链路记录**；
- 客户免 taskid、按 cid 维度自助查询：这些设备在有效期内**所有消息**的推送情况（是否下发、是否到达、失败原因）；
- 不为全量客户设备记录链路日志，**大幅降低存储压力**。

### 1.3 核心矛盾

| 维度 | 现状 | 目标 |
|---|---|---|
| 采集范围 | 全量设备 | 仅客户登记的白名单设备（每客户 ≤ 20 个） |
| 查询维度 | taskid + cid（单条消息） | **仅 cid**（该设备一段时间内全部消息） |
| 保留时长 | 7 天（全量，成本高） | 白名单设备 7或30 天（按需，成本可控） |

---

## 2. 目标与非目标

**目标**

1. 白名单设备的消息链路事件在 7/30 天内可查，客户自助、免人工；
2. 非白名单设备不记录链路明细，存储总量与 SVIP 客户数（而非消息总量）挂钩；
3. 白名单登记生效时间 ≤ 5 分钟（准实时），到期自动清理。

**非目标**

- 不改变下发主链路的既有功能与语义（打标只增不改，且必须可降级旁路）；
- 不在本方案内解决"非白名单设备的历史消息回溯"（历史消息查询见方案二，仅近 3 天）。

---

## 3. 总体架构

```
开发者平台(SVIP 前端)
   │ 上传 cid 列表 / 查询请求
   ▼
┌──────────────────┐     白名单分发      ┌────────────────────────────┐
│ 白名单管理服务     │ ─────────────────▶ │ 各机房下发链路模块            │
│ (归属校验/有效期)  │   (配置中心/Redis)  │ psc / sdp / gtps-* / gtpr   │
└──────────────────┘                     │ omp / as：命中白名单才落链路事件│
                                         └──────────┬─────────────────┘
                                                    │ 异步写
                                                    ▼
                              ┌─────────────────────────────────┐
                              │ 链路存储（冷热分层）               │
                              │  热：Redis（24h~7d，TTL）         │
                              │  冷：KV/列式存储（30d，按 cid 聚合）│
                              └──────────────┬──────────────────┘
                                             │
                              ┌──────────────▼──────────────────┐
                              │ 链路查询服务（按 cid 聚合 + 时间线）│
                              └──────────────┬──────────────────┘
                                             ▼
                                   开发者平台 SVIP 页面
```

## 4. 核心流程

### 4.1 设备登记（客户 → 白名单）

1. 客户在 SVIP 页面上传 10~20 个 cid（有效期建议默认 7 天，可选购 30 天）；
2. 提交服务校验：cid 格式（32 位十六进制）、**cid 归属 appid 必须等于客户自身应用**（复用故障排查「状态查询」既有的 cid→归属Appid/包名 解析能力，防止跨客户登记他人设备）、SVIP 权限；
3. 校验通过后写入白名单存储，并分发至各机房链路模块的采集开关（目标生效 ≤ 5 分钟）；
4. 有效期到期自动移出白名单，关联链路数据随 TTL/生命周期清理。

### 4.2 按需采集（下发链路打标）

消息下发路径各环节（个推入口受理 → SDP 厂商策略 → 厂商离线通道 → 厂商回执 gtpr / 在线回执 as → 离线库 omp）在产生链路事件前**先判定 cid 是否在白名单**：

- 命中 → 写链路事件（热存储），异步落冷；
- 未命中 → 走原逻辑，不落明细；
- **白名单判定失败（Redis 异常等）必须降级为"不采集"，绝不能阻塞下发主流程**。

判定方式建议：链路模块**本地缓存白名单**（定时/推送刷新，秒级~分钟级延迟可接受），避免每条消息一次远程查询。

### 4.3 自助查询（客户 → 时间线）

1. 客户输入 cid（已在白名单内）+ 时间范围（≤ 保留期）；
2. 查询服务按 cid 聚合出该设备的**消息列表**（每条消息含 taskid、推送时间、到达状态摘要）；
3. 点开单条消息展示完整链路时间线 + 失败原因（文案化）；
4. 免 taskid 是本方案对客户的核心体验提升。

## 5. 研发改动清单与评估点

| # | 模块 | 改动 | 关键评估点 |
|---|---|---|---|
| 1 | 白名单管理服务 | 登记接口、归属校验、有效期管理、白名单存储与分发 | 白名单容量上限（建议先按 1 万 cid 设计）；分发延迟；与开发者平台账号体系打通 |
| 2 | 下发链路各模块（psc/sdp/gtps-*/gtpr/as/omp） | 链路事件产出前增加白名单判定，命中才写明细 | **主链路性能**：判定走本地缓存后为一次内存查询，理论开销可忽略，需压测确认 P99 无回退；打标异常必须旁路降级，不阻塞下发 |
| 3 | 链路存储 | 热冷分层：热（Redis，24h~7d）+ 冷（30 天）；写入改异步双写 | 冷存储选型（HBase / Cassandra / ClickHouse / 对象存储+索引，按查询模式"按 cid 聚合、按时间倒排"定）；写入放大与削峰 |
| 4 | 链路查询服务 | 按 cid 聚合查询接口（消息列表 + 单条链路 + 失败原因文案） | 免 taskid 聚合的索引设计（cid 为主键、时间倒排）；大客户长尾延迟 |
| 5 | 开发者平台 | SVIP 入口对接（登记页、查询页、进度展示） | 与账号/SVIP 权限体系打通；前端批量交互 |
| 6 | 多机房 | 白名单跨机房分发；链路数据按机房归属聚合 | 分发延迟窗口内的漏采（登记前已下发的消息不补采，需在产品文案说明） |

**需要研发明确的决策点**

1. 白名单判定的具体实现：cid 白名单量级小（万级以内），建议 **Redis Set + 模块本地缓存**即可，无需布隆过滤器（布隆不支持删除，与"到期清理"冲突）；
2. 冷存储选型与查询索引方案；
3. 链路事件格式是否沿用现有 Redis 结构（建议保持一致，降低查询服务与历史数据兼容成本）；
4. 登记前已下发、登记后才查询的消息是否补采（建议：不补采，仅登记后新增消息可查，产品侧明示）。

## 6. 运维清单

| # | 事项 | 说明 |
|---|---|---|
| 1 | Redis 容量与淘汰策略 | 链路数据建议独立实例或独立 DB；淘汰策略必须评估（`noeviction` + TTL 到期清理，避免 hot 数据被 evict 造成链路断档） |
| 2 | 冷存储运维 | 选型后的部署、备份、容量水位、生命周期（30 天到期删除） |
| 3 | 监控告警 | 采集量（白名单命中数）、存储水位、白名单分发延迟、查询成功率与延迟、打标降级次数（降级突增说明白名单存储故障） |
| 4 | 白名单分发通道 | 配置中心或 Redis pub/sub 的可用性 |

## 7. 容量估算模型（示例数字需实测修正）

**公式**

```
日增链路事件量 ≈ Σ (白名单设备数 × 设备日均消息数 × 单消息链路行数 × 单行大小)
```

**参数假设（示例，需用真实 SVIP 客户画像修正）**

- SVIP 客户 100 家 × 每家 ≤ 20 cid = 白名单设备 ≤ 2,000 个；
- 每设备日均消息 50 条（测试设备场景通常远低于此）；
- 单消息链路 6~10 行（受理→入口→sdp→厂商→回执，取 8）；
- 单行 0.2~1 KB（含字段与开销，取 0.5 KB）。

| 规模 | 日增 | 7 天（热） | 30 天（冷） |
|---|---|---|---|
| 基准（上述假设） | ≈ 400 MB | ≈ 2.8 GB | ≈ 12 GB |
| ×10（消息量/客户数放大） | ≈ 4 GB | ≈ 28 GB | ≈ 120 GB |
| ×100 | ≈ 40 GB | ≈ 280 GB | ≈ 1.2 TB |

**结论**：基准量下 Redis 热 7 天（约 3 GB）可承受但建议只放 24~48h 热 + 冷存储承担 7~30 天明细；×10 以上必须冷热分层，且冷存储是成本大头。**存储总成本首次与"SVIP 客户数 × 白名单设备数"挂钩，与全量消息量解耦**——这是本方案相对现状（全量记录）的核心收益。

## 8. 关键风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 打标侵入下发主链路 | 下发延迟/稳定性回退 | 本地缓存判定；异常旁路降级；全链路压测 |
| 白名单分发延迟 | 登记后几分钟内消息漏采 | 产品文案明示"登记后生效"；分发延迟监控 |
| 冷存储选型不当 | 查询慢/成本高 | 先明确查询模式（按 cid 点查、时间倒排），再选型 |
| 客户误登记他人 cid | 数据越权 | 登记时强制 cid→appid 归属校验（能力已有） |
| 长期存储成本随 SVIP 增长 | ×100 规模达 TB 级 | 有效期上限、每客户 cid 上限、到期强清理 |

## 11. 与方案二的对比与组合建议

| 维度 | 方案一（本方案） | 方案二（异步队列查询） |
|---|---|---|
| 客户体验 | ★★★★★ 免 taskid、7/30 天可查、一次查全部消息 | ★★★☆ 近 3 天、窗口查询较慢 |
| 研发投入 | 大（采集打标 + 存储改造 + 查询服务） | 小（基本不需要研发改下发/存储链路） |
| 上线周期 | 2~3 个月 | 1~2 周 MVP |
| 存储成本 | 新增冷热分层（与 SVIP 规模挂钩） | 0（复用现有日志系统，仅近 3 天） |
| 对现有系统风险 | 下发主链路改造，需压测 | 无侵入 |

**组合建议**：先用**方案二**以最小成本上线 MVP、验证 SVIP 客户真实需求与查询量；需求成立后，研发按本方案完成存储改造，将产品升级为"免 taskid + 7/30 天 + 按需采集"的完整形态。两者不冲突，是同一产品的两个阶段。
