# 方案二：基于消息队列的异步限流查询服务（消息链路查询 SVIP 对外服务）

| 项目 | 内容 |

| 评估/配合部门 | **运维部门**（MQ 选型部署、Worker 部署、对外网关、监控）；研发部门仅需少量配合（cid 归属校验接口确认、SVIP 权限对接） |
| 文档状态 | 待评估（V1.0，2026-10-27） |

## 1. 背景与约束

### 1.1 需求

客户（开发者）在开发者平台 SVIP 入口**批量上传 10~20 个设备 cid**，自助查询这些设备的消息下发链路情况（是否下发、是否到达、失败原因）。

### 1.2 现有日志系统的硬约束（方案设计的前提）

| 约束 | 说明 | 对外服务的应对 |
|---|---|---|
| **并发上限 2** | 日志查询平台同一时刻只能执行 2 个查询任务 | 请求必须**异步排队**，不能同步等待 |
| **账号维度隔离** | 个推账号按应用（appid）区分，**一次只能提交一个**（关键字 + 时间窗）查询 | Worker 按 appid 维度排队调度，全局并发收敛到 2 |
| **日志仅保留近 3 天** | 超过 3 天的日志不可查 | 产品文案明示"仅支持近 3 天"；历史回溯走方案一 |
| 单次查询耗时分钟级 | 当天消息 2~5 分钟；跨天/大窗口 5~20 分钟 | 任务状态机 + 前端进度展示，禁止同步阻塞 |

### 1.3 可复用的内部资产（技术支持部门已验证）

技术支持部门内部已有成熟的链路查询与判读工具，以下能力**已在线上工单长期实战验证**，本方案直接复用：

- 流式分批查询编排（逐批推进、探测早停、厂商通道自动二轮查询）；
- **厂商错误码/回执码判读知识库**：华为/小米/OPPO/vivo/荣耀/鸿蒙/FCM 数百个错误码与回执码的释义及处置建议（如华为 110256=单设备日限且细分资讯营销类、小米 27001=channel 信息不匹配等）；
- 规则判读与结论生成（在线/离线/假在线/无 device token/频控等确定性规则 + 大模型兜底）；
- 查询结果 30 分钟缓存（同参数去重，避免重复消耗日志系统并发额度）；
- 历史消息查询的等待放大机制（跨天窗口自动放大轮询上限至 20 分钟）。

**即：本方案的核心工程量在"队列化、限流、对外安全"，查询与判读能力是现成的。**

---

## 2. 目标与非目标

**目标**

1. SVIP 客户批量提交 ≤ 20 个 cid，异步完成查询并自助查看结果（含链路时间线与失败原因）；
2. 对日志系统的并发压力收敛到上限 2，且按 appid 公平调度，防止单客户占满；
3. MVP 快速上线（1~2 周），不改日志系统、不改下发链路、不新增长期存储。

**非目标**

- 不提供 3 天以上历史查询（受日志系统保留期约束，升级路线见方案一）；
- 不承诺实时出结果（分钟级异步，见 §7 容量估算）。

## 3. 总体架构

```
开发者平台 SVIP 前端
   │ 批量上传 cid（≤20）+ 可选推送时间/taskid
   ▼
┌────────────────────┐
│ 提交服务（BFF）      │  SVIP 权限校验、cid 格式校验、
│                    │  cid→appid 归属校验（防跨客户）、
│                    │  参数指纹去重、生成任务族
└─────────┬──────────┘
          │ 写入
          ▼
┌────────────────────┐
│ 消息队列             │  Kafka / Redis Stream（选型见 §5）
│ 按 appid 分队列/分区  │
└─────────┬──────────┘
          │ 消费（受全局信号量约束）
          ▼
┌────────────────────┐        ┌──────────────────┐
│ 查询调度 Worker      │ ──────▶ │ 日志查询平台        │
│ 全局并发 = 2         │  查询   │ （X-API-Key 凭证）  │
│ appid 维度配额/公平   │        └──────────────────┘
│ 超时/重试/缓存        │
│ 规则判读 + 结论生成    │
└─────────┬──────────┘
          │ 结果写
          ▼
┌────────────────────┐
│ 结果存储（Redis/MySQL）│  任务状态 + 链路时间线 + 结论（保留 7~30 天）
└─────────┬──────────┘
          ▼
   前端轮询任务进度 / 展示时间线与结论
```

## 4. 两种查询形态（均支持）

日志查询平台要求"关键字 + 时间窗"，据此对客户提供两种形态：

| | **精确查询**（推荐默认） | **窗口查询** |
|---|---|---|
| 客户输入 | cid + 推送时间点（或 taskid + cid） | 仅 cid |
| 查询窗口 | 推送时间 -15 分钟 ~ +60 分钟 | 近 3 天（覆盖该 cid 全部消息） |
| 单次耗时（实测参考） | **2~5 分钟**（内部实测：2 分 54 秒 / 3 分 12 秒 / 4 分 37 秒） | **5~20 分钟**（跨天窗口自动放大轮询等待） |
| 适用场景 | 客户知道"哪条消息、大概什么时候发的"（工单场景最常见） | 客户只想看"这台设备最近收推送正常吗" |
| 交互建议 | 前端按 cid 列表逐行填时间点 | 一键批量，结果按消息逐条展示 |

**批量流程**：客户上传 10~20 个 cid → 每个 cid 生成一个子任务 → 任务族整体展示进度（已完成 n/20）→ 单条失败不影响其他条。

## 5. 消息队列选型

| 维度 | Kafka | Redis Stream |
|---|---|---|
| 吞吐/持久化 | 极高、磁盘持久化 | 中等、内存为主（可 AOF） |
| 消费模型 | 消费组、分区有序 | 消费组、按 Stream 有序 |
| 运维成本 | 若公司已有集群则零成本 | 已有 Redis 依赖，几乎零新增 |
| 延迟积压风险 | 低 | 需关注内存水位 |
| 适用判断 | 消息量大、需长期回放 | **本场景量小（SVIP 查询任务），够用** |

**建议**：运维已有 Kafka 集群则直接复用（按 appid 做 partition key 天然实现账号维度排队）；否则 **Redis Stream 即可满足**（本方案任务量级为"次/分钟"，远非高吞吐场景），不为此新建 Kafka。最终以运维意见为准。

## 6. 核心机制设计

### 6.1 任务模型与状态机

```
任务族（一次批量提交）
 └─ 子任务 per cid：queued → running → done / failed / partial
```

- 前端展示任务族进度（n/20 完成）；单条失败给出原因（超时/无日志/参数错误），不影响其他子任务；
- 子任务结果保留 7~30 天（结果存储体量极小：每任务 KB 级）。

### 6.2 限流与公平调度

- **全局并发信号量 = 2**（对齐日志系统上限，可配置）；
- **appid 维度排队**：每个 appid 一个队列，Worker 轮转消费（加权轮询），单 appid 最大在跑数 = 1，防止单客户占满全局并发；
- 优先级：可预留 SVIP 等级字段，当前全部同权；
- 队列深度保护：单 appid 排队上限（如 100），超出直接拒绝并提示稍后再试。

### 6.3 去重与缓存

- 参数指纹（appid+cid+时间窗+形态）30 分钟 LRU 缓存，命中直接返回，不消耗并发额度；
- 同客户短时间内重复提交同参数 → 合并到已有任务族。

### 6.4 超时与重试

- 精确查询超时 8 分钟；窗口查询超时 25 分钟（含日志系统排队与等待放大）；
- 失败自动重试 1 次（换队列尾部），仍失败标记 failed 并给可读原因；
- "查询完成但窗口内无日志"是正常结果（该设备近期无推送/参数有误），如实呈现并提示核对，不算失败。

### 6.5 结论生成（对客户可读化）

- 复用规则判读：命中确定性证据（厂商回执/错误码/失败行）直接出结论，其余走大模型兜底；
- **对外文案需脱敏转换**：内部模块名/字段（psc、sdp、gtpr、rp-bi 等）转为客户视角描述（"个推受理 → 厂商通道下发 → 设备回执"），错误码给出原因与处置建议（判读知识库已覆盖）；
- 不暴露内部 IP、服务器名、账号凭证等敏感字段。

## 7. 安全与合规

| # | 事项 | 方案 |
|---|---|---|
| 1 | **跨客户数据隔离**（最高优先级） | 提交时强制校验每个 cid 的归属 appid = 提交者应用（复用开发者平台故障排查已有的 cid→归属Appid/包名解析能力）；校验不通过的 cid 拒绝并在结果中提示 |
| 2 | 鉴权 | 复用开发者平台登录态 + SVIP 权限标识；BFF 校验后才入队 |
| 3 | 内网系统不直暴 | 日志查询平台仅内网可达；对外仅暴露 BFF 的 HTTPS 接口，Worker 用 X-API-Key 凭证访问内网平台（凭证由运维保管、定期轮换） |
| 4 | 审计 | 记录"谁、何时、查了哪些 cid"，保留 ≥ 180 天 |
| 5 | 限流防滥用 | 按 appid 限每日提交量（如 500 子任务/日），防刷 |

## 8. 容量与 SLA 估算（示例数字需按真实客户量修正）

**吞吐模型**

```
全局吞吐 ≈ 并发 2 ÷ 单查询耗时
  精确查询（均值 4 分钟）≈ 30 查询/小时
  窗口查询（均值 10 分钟）≈ 12 查询/小时
批量 20 cid 全窗口查询 ≈ 20 × 10 ÷ 2 ≈ 100 分钟出全（精确查询 ≈ 40 分钟）
```

**结论与产品建议**

- 单客户批量必须在**异步 + 进度条**形态下交付，任何"同步等待"的交互都不可行；
- 排队时长与 SVIP 客户数线性相关：按 30 查询/小时估算，10 家 SVIP 客户各提交 1 批/日（20 精确查询）= 200 查询/日 ≈ 7 小时机器时间，**当天可消化**；若客户量增长 10 倍，需与日志平台方评估并发上限扩容（这是方案二的上限，也是升级方案一的信号之一）；
- 结果存储可忽略不计（KB 级/任务）。

## 10. 局限性与升级路径

| 局限 | 说明 | 升级方向 |
|---|---|---|
| 仅近 3 天 | 日志系统保留期决定 | 方案一存储改造后解锁 7/30 天 |
| 吞吐上限 | 全局并发 2 | 与日志平台协商扩容；或方案一查询走独立链路数据不再依赖日志系统 |
| 大窗口查询慢 | 窗口查询 5~20 分钟 | 引导客户优先用精确查询；产品默认勾选时间点 |
| 依赖内部日志系统 SLA | 日志系统抖动直接影响对外 | Worker 熔断与排队缓冲；对外 SLA 定为"尽力而为"级 |

**升级路径**：本方案 MVP 验证 SVIP 客户需求与查询量后，研发按《方案一》完成按需采集与存储改造，查询入口从"日志系统查询"切换为"链路数据查询"，前端交互与任务体系可完全复用。

## 12. 与方案一的对比（摘要）

| 维度 | 方案二（本方案） | 方案一（按需采集+存储改造） |
|---|---|---|
| 上线周期 | 1~2 周 MVP | 2~3 个月 |
| 研发投入 | 极小 | 大（下发链路打标 + 存储改造） |
| 可查范围 | 近 3 天 | 7/30 天 |
| 查询维度 | cid（+推荐时间点） | cid 免 taskid 全量消息 |
| 吞吐 | 受日志系统并发 2 限制 | 独立链路数据，查询快 |
| 存储成本 | ≈ 0 | 冷热分层（与 SVIP 规模挂钩） |

**组合建议**：方案二作为一期 MVP 快速上线并验证需求；方案一作为二期完整形态。两个方案不冲突，前端交互与任务体系可平滑迁移。
