## 1. 背景与约束

### 1.1 需求

在开发者平台 SVIP 入口向客户提供**单条消息链路自助查询**：

- 客户输入三要素：**taskid（消息任务号）+ cid（设备号）+ 推送时间点**；
- 系统提交上游日志系统查询该消息的下发链路日志，并通过**既定规则判读（辅以大模型）**自动生成链路结论——是否正常下发、是否到达设备、失败原因与处置建议；
- 查询异步执行、自助获取结果，无需技术支持人工介入。

即：把技术支持内部已长期使用的链路查询工具（logseek）的查询与判读能力，包装为对外的自助服务。

### 1.2 现有日志系统的硬约束（方案设计的前提）

| 约束 | 说明 | 对外服务的应对 |
|---|---|---|
| **并发上限 2** | 日志查询平台同一时刻只能执行 2 个查询任务 | 客户请求必须**异步排队**，不能同步等待 |
| **账号维度隔离** | 个推账号按应用（appid）区分，一次只能提交一个查询 | Worker 按 appid 维度排队调度，全局并发收敛到 2 |
| **单账号单任务** | 单次查询为分钟级耗时任务，**每个账号同一时刻只能提交一个查询，完成（或失败）后才能再次提交** | 提交服务按 appid 检查进行中任务，存在即拒绝并提示预计剩余时间；前端进行中时提交按钮置灰 |
| **日志仅保留近 3 天** | 超过 3 天的日志不可查 | 提交时校验推送时间点，产品文案明示"仅支持近 3 天" |
| 单次查询耗时分钟级 | 常态 2~5 分钟（内部实测：2 分 54 秒 / 3 分 12 秒 / 4 分 37 秒） | 任务状态机 + 前端进度展示，禁止同步阻塞 |

### 1.3 可复用的内部资产（技术支持部门已验证）

技术支持部门内部链路查询工具（logseek）已在线上工单长期实战验证，以下能力**直接复用**，本方案的工程量集中在"队列化、限流、对外安全"：

- 单条查询全流程：taskid 前缀自动识别推送类型（单推/列表推/全推）→ 查询窗口自动生成（推送时间 -15 分钟 ~ +60 分钟）→ 流式分批查询（探测早停、厂商通道自动二轮查询、回执收口等优化）→ 规则判读/大模型生成结论；
- **厂商错误码/回执码判读知识库**：华为/小米/OPPO/vivo/荣耀/鸿蒙/FCM 数百个错误码与回执码的释义及处置建议（如华为 110256=单设备日限（资讯营销类）、小米 27001=channel 信息不匹配等）；
- 查询结果 30 分钟缓存（同参数去重，不重复消耗日志系统并发额度）。

---

## 2. 目标与非目标

**目标**

1. SVIP 客户提交单条（taskid + cid + 推送时间点）查询，异步完成并自助查看链路时间线与结论；
2. 对日志系统的并发压力收敛到上限 2，按 appid 公平调度，防止单客户占满；
3. **单账号同一时刻仅允许一个进行中查询**（耗时任务，完成前禁止再次提交）；
4. MVP 快速上线（1~2 周），不改日志系统、不改下发链路、不新增长期存储。

**非目标**

- 不提供 3 天以上历史查询（受日志系统保留期约束，升级路线见方案一）；
- 不承诺实时出结果（分钟级异步，见 §8 容量估算）；
- 不支持免 taskid 的设备维度聚合查询（那是方案一的形态，需要存储改造支撑）。

## 3. 总体架构

```
开发者平台 SVIP 前端
   │ 输入 taskid + cid + 推送时间点（单条）
   ▼
┌────────────────────┐
│ 提交服务（BFF）      │  SVIP 权限校验、taskid/cid 格式校验、
│                    │  时间点范围校验（≤3 天）、参数指纹去重
└─────────┬──────────┘
          │ 写入
          ▼
┌────────────────────┐
│ 消息队列             │  Kafka / Redis Stream（选型见 §5）
│ 按 appid 分队列/分区  │
└─────────┬──────────┘
          │ 消费（受全局信号量约束）
          ▼
┌────────────────────┐        ┌──────────────────┐
│ 查询调度 Worker      │ ──────▶ │ 日志查询平台        │
│ 全局并发 = 2         │  查询   │ （X-API-Key 凭证）  │
│ appid 维度配额/公平   │        └──────────────────┘
│ 超时/重试/缓存        │
│ 规则判读 + 结论生成    │
└─────────┬──────────┘
          │ 结果写
          ▼
┌────────────────────┐
│ 结果存储（Redis/MySQL）│  任务状态 + 链路时间线 + 结论（保留 7~30 天）
└─────────┬──────────┘
          ▼
   前端任务状态页（排队中 → 查询中 → 已完成）
   完成后展示链路时间线 + 结论
```

## 4. 单条查询的输入与系统行为

客户只需要填三个字段，其余全部由系统自动处理：

| 客户输入 | 校验 | 说明 |
|---|---|---|
| taskid | 前缀自动识别推送类型（单推 RASS_/列表推 RASL_/全推 RASA_ 等） | 列表推/全推必须同时提供 cid |
| cid | 32 位十六进制格式校验 | |
| 推送时间点 | 必须在近 3 天内 | 超出范围提交时直接拒绝并提示 |

**系统内部自动完成（客户无感）**：

1. 查询窗口生成：推送时间点 -15 分钟 ~ +60 分钟，自动截断与校验；
2. 推送类型与入口模块识别（按 taskid 前缀路由到对应入口）；
3. 流式分批查询：逐批推进、窗口内无日志早停、未指定机型时按离线策略决策结果自动二轮查询对应厂商通道与回执；
4. 规则判读 + 结论生成：命中确定性证据（厂商回执、错误码、失败日志）直接出结论，其余大模型兜底；
5. 输出：链路时间线（个推受理 → 个推下发 → 厂商通道下发 → 设备回执/失败）+ 结论 + 失败原因与处置建议。

**前端交互建议**：提交后进入任务状态页（排队中 → 查询中 → 已完成/失败，展示预计等待）；**任务进行中提交按钮置灰、禁止再次提交**（单账号单任务，见 §6.2）；完成后展示时间线与结论，历史任务可回看（结果保留 7~30 天）。

## 5. 消息队列选型

| 维度 | Kafka | Redis Stream |
|---|---|---|
| 吞吐/持久化 | 极高、磁盘持久化 | 中等、内存为主（可 AOF） |
| 消费模型 | 消费组、分区有序（按 appid 做 partition key 天然实现账号维度排队） | 消费组、按 Stream 有序 |
| 运维成本 | 若公司已有集群则零成本 | 已有 Redis 依赖，几乎零新增 |
| 适用判断 | 消息量大、需长期回放 | 本场景任务量小（次/分钟级），够用 |

**建议**：运维已有 Kafka 集群则直接复用；否则 **Redis Stream 即可满足**，不为此新建 Kafka。最终以运维意见为准。

## 6. 核心机制设计

### 6.1 任务模型与状态机

每个查询任务一条记录：

```
queued（排队中）→ running（查询中）→ done（已完成）/ failed（失败）
```

- 任务记录含：提交人/appid、taskid/cid/时间点、当前状态、排队位置、结果（时间线 + 结论）、失败原因；
- 结果保留 7~30 天（单任务 KB 级，存储可忽略）。

### 6.2 单账号单任务约束（提交侧准入）

单次查询是分钟级耗时任务，**每个账号（appid）同一时刻只允许一个进行中的查询，完成后才能再次提交**：

- 提交服务在入队前检查该 appid 是否已有进行中任务（queued/running 均算）：存在则拒绝本次提交，返回进行中任务的状态与预计剩余时间；
- 任务进入终态（done/failed）即解锁，可提交下一个；超时/失败同样解锁，不出现"卡死无法再提交"；
- 前端配合：任务进行中提交按钮置灰并展示剩余时间，完成/失败后恢复；
- 与 §6.3 调度侧的并发收敛（全局信号量 = 2）呼应：**提交侧管准入（一账号一任务），调度侧管执行（并发收敛到日志系统上限）**，两层共同保证日志系统压力可控。

### 6.3 限流与公平调度

- **全局并发信号量 = 2**（对齐日志系统上限，可配置）；
- **appid 维度排队**：每个 appid 一个队列，Worker 轮转消费；由于 §6.2 的单账号单任务约束，每个 appid 在队列中至多存在 1 个任务（queued/running 合计），公平性由约束天然保证；
- 队列深度保护：**全局**排队上限（如 200），超出直接拒绝并提示错峰再试（防整体过载）。

### 6.4 去重与缓存

- 参数指纹（appid + taskid + cid + 时间点）30 分钟 LRU 缓存：命中直接返回结果，不消耗并发额度；
- 同客户短时间内重复提交同参数 → 直接返回已有任务。

### 6.5 超时与重试

- 单查询超时 8 分钟（含日志系统排队与轮询）；超时自动重试 1 次，仍失败标记 failed 并给可读原因；
- "查询完成但窗口内无日志"是正常结果（该时间点附近无此消息，或 taskid/cid/时间填写有误），如实呈现并提示核对，不算失败。

### 6.6 结论生成（对客户可读化）

- 规则判读优先：错误码/回执码命中知识库直接生成结论（快且稳定），其余走大模型兜底；
- **对外文案脱敏转换**：内部模块名/字段（psc、sdp、gtpr、rp-bi 等）转为客户视角描述（"个推受理 → 厂商通道下发 → 设备回执"），错误码给出原因与处置建议；
- 不暴露内部 IP、服务器名、账号凭证等敏感字段。

## 7. 安全与合规

| # | 事项 | 方案 |
|---|---|---|
| 1 | 鉴权 | 复用开发者平台登录态 + SVIP 权限标识；BFF 校验后才入队 |
| 2 | 数据边界 | 客户只能查自己应用的 taskid/cid（提交时校验 taskid/cid 归属 appid；归属校验能力开发者平台已具备，需确认接口） |
| 3 | 内网系统不直暴 | 日志查询平台仅内网可达；对外仅暴露 BFF 的 HTTPS 接口，Worker 用 X-API-Key 凭证访问内网平台（凭证由运维保管、定期轮换） |
| 4 | 审计 | 记录"谁、何时、查了什么"，保留 ≥ 180 天 |
| 5 | 限流防滥用 | 单账号单任务（§6.2）+ 按 appid 限每日提交量（如 100 次/日），双重防刷 |

## 8. 容量与 SLA 估算（示例数字需按真实客户量修正）

**吞吐模型**

```
全局吞吐 ≈ 并发 2 ÷ 单查询耗时
  单查询常态 2~5 分钟（内部实测 2 分 54 秒 / 3 分 12 秒 / 4 分 37 秒）
  → 全局 ≈ 24~60 查询/小时（按均值 4 分钟计 ≈ 30 查询/小时）
  → 理论日容量 ≈ 700+ 查询/天（24 小时）；按工作时间 12 小时计 ≈ 360 查询/天
排队时长 ≈ 排队任务数 × 单查询均耗时 ÷ 2
  例：队列中 10 个任务 → 平均等待约 20 分钟
```

**结论与产品建议**

- 单条查询分钟级完成，前端必须**异步 + 状态页**交付，禁止同步等待；
- **单账号单任务约束（§6.2）天然限制单客户提交速率**（最快约 2~5 分钟一条），与每日总量限流互补，共同防刷；
- 排队体验：状态页实时展示"前方还有 N 个任务"，超过阈值（如 >15 分钟）提示错峰提交；
- 按 30 查询/小时估算，几十家 SVIP 客户的低频自助查询（日均数百次）当天可消化；若查询量增长到日千次以上，需与日志平台方评估并发上限扩容——这是方案二的容量上限，也是升级方案一的信号之一。

## 10. 局限性与升级路径

| 局限 | 说明 | 升级方向 |
|---|---|---|
| 仅近 3 天 | 日志系统保留期决定 | 方案一存储改造后解锁 7/30 天 |
| 需客户提供推送时间点 | 客户须从业务侧拿到"哪条消息、何时推送" | 工单场景通常可拿到；无法提供时间点的场景走方案一的设备维度查询 |
| 吞吐上限 | 全局并发 2 | 与日志平台协商扩容；或方案一查询走独立链路数据，不再依赖日志系统 |
| 依赖内部日志系统 SLA | 日志系统抖动直接影响对外 | Worker 熔断与排队缓冲；对外 SLA 定为"尽力而为"级 |

**升级路径**：本方案 MVP 验证 SVIP 客户需求与查询量后，研发按《方案一》完成按需采集与存储改造，查询入口从"日志系统实时查询"切换为"链路数据查询"，前端交互与任务体系可完全复用。

## 12. 与方案一的对比（摘要）

| 维度 | 方案二（本方案） | 方案一（按需采集+存储改造） |
|---|---|---|
| 查询形态 | 单条：taskid + cid + 推送时间点 | 设备维度：免 taskid，查白名单设备一段时间内全部消息 |
| 可查范围 | 近 3 天 | 7/30 天 |
| 查询耗时 | 分钟级（排队 + 2~5 分钟） | 秒级（查现成链路数据） |
| 研发投入 | 极小（查询/判读能力现成） | 大（下发链路打标 + 存储改造 + 聚合查询服务） |
| 上线周期 | 1~2 周 MVP | 2~3 个月 |
| 吞吐 | 受日志系统并发 2 限制 | 独立链路数据，并发可横向扩展 |
| 存储成本 | ≈ 0 | 冷热分层（与 SVIP 规模挂钩） |

**组合建议**：方案二作为一期 MVP 快速上线并验证 SVIP 客户真实需求与查询量；方案一作为二期完整形态。两个方案不冲突，前端交互与任务体系可平滑迁移。
